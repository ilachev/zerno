# Пример: публичный каталог документов

Тип: `design`. Статус: `accepted-plan`. Сверено с кодом: 2026-10-17.

## Задача и границы

Пример проверяет, достаточно ли небольшого HTTP/PDO-ядра для полезного серверного сайта. Посетитель открывает список опубликованных документов, читает карточку и скачивает файл. На следующем самостоятельном этапе редактор входит, создаёт черновик с PDF и публикует его. Все основные действия доступны без JavaScript.

Это тонкое приложение вне `src/Platform`, а не новая CMS внутри ядра. Предлагаемое место — отдельный `examples/document-catalog/` со своей конфигурацией, маршрутами, обработчиками, шаблонами, SQL и миграциями. Такого каталога пока нет; его autoload и включение в поставку должны быть определены при реализации. Общие изменения извлекаются в ядро только после появления необходимого повторно используемого контракта.

Пример следует [назначению проекта](./vision.md), использует [текущую архитектуру](../architecture/overview.md) и проверяет шаги из [дорожной карты](./roadmap.md). Команды запуска и проверки берутся из [инфраструктуры и тестирования](../development/infrastructure-and-testing.md); этот дизайн не добавляет фиктивных runnable-команд.

## Самостоятельный первый этап: публичное чтение

Первый этап не зависит от реализации входа, CSRF, upload UI или универсального кеша. Опубликованные записи и тестовые файлы создаются контролируемой fixture/import процедурой приложения. Нельзя добавлять публичный endpoint для их создания ради обхода ещё не готового редактора.

| Предлагаемый маршрут | Поведение |
| --- | --- |
| `GET /documents` | Ограниченный список опубликованных записей с устойчивым порядком и обычной навигацией страниц |
| `GET /documents/{id}` | HTML-карточка опубликованного документа: название, описание, дата публикации, сведения о файле и ссылка скачивания |
| `GET /documents/{id}/download` | Потоковая выдача файла после проверки состояния документа и связи с файлом |
| `HEAD` для этих ресурсов | Те же определённые метаданные ответа без выдачи тела |

Имена маршрутов пока относятся к дизайну примера. Для отсутствующей, непубличной или некорректно указанной записи приложение возвращает определённую публичную ошибку без раскрытия черновика или storage path. HTML-страницы и ошибки имеют соответствующий content type. Обычный публичный запрос не создаёт сессию и `Set-Cookie`.

Для начала допустимо читать БД на каждом запросе без общего cache. Политика HTTP-кеширования задаётся явно; длительная публичная freshness не включается до согласования снятия с публикации. Такой этап уже позволяет измерить HTML, SQL и потоковую выдачу, проверить доступность и использовать пример как контроль перед добавлением редактора.

## Роли и разрешения следующего этапа

| Участник | Разрешённые действия |
| --- | --- |
| Посетитель | Читать и скачивать только опубликованное |
| Редактор | Создать и изменить черновик, загрузить допустимый файл, опубликовать и снять свою доступную запись с публикации согласно политике примера |
| Оператор | Подготовить конфигурацию и учётные записи, выполнить миграции, backup/restore и техническое обслуживание вне публичных routes |

Начальный пример может предоставить одному редактору весь этот ограниченный набор действий. Разделение автора и согласующего, сложная ролевая иерархия, делегирование и универсальная admin UI не нужны. Сервер всё равно проверяет конкретное разрешение и объект для каждого действия; скрытая кнопка не считается авторизацией.

Источник учётных записей выбирается до защищённого этапа. При локальных паролях понадобятся поддерживаемые средства PHP для хеширования/проверки, настройка стоимости, ограничение попыток и определённая процедура восстановления доступа. Дизайн не закрепляет SSO, MFA, внешнего identity provider или собственную криптографию.

## Состояния и данные

Предлагаемый минимальный документ содержит идентификатор, название, краткое текстовое описание, состояние, ссылку на файл, timestamps и номер изменения для контроля конкуренции. Файл имеет непрозрачный storage key, безопасное отображаемое имя, проверенный тип, размер и hash. Названия таблиц и generated PHP-классов ещё не определены.

| Состояние документа | Видимость и переходы |
| --- | --- |
| `draft` | Доступен разрешённому редактору; можно менять данные и вложение. Публикация разрешена только с готовым проверенным файлом |
| `published` | Появляется в публичных списке, карточке и download route. В первой версии содержимое и файл фиксируются; допускается снятие с публикации |
| `withdrawn` | Не выдаётся новым публичным запросам. Данные и audit сохраняются до отдельно определённого обслуживания |

Повторная публикация, замена уже опубликованного содержимого и редакционные версии требуют отдельного решения. Номер изменения для optimistic concurrency не следует автоматически считать полноценной историей версий. В первой реализации можно потребовать новый документ для новой публикации, не создавая общий workflow engine.

Все публичные SQL-запросы ограничены опубликованным состоянием. Download не получает произвольный file path из URL и не ограничивается проверкой существования blob. Закрытый файл не становится публичным из-за того, что его идентификатор угадан.

## Защищённый пользовательский поток

1. Редактор входит; identity и проверка разрешений подключаются только к соответствующей композиции. При входе исключается повторное использование прежней неаутентифицированной сессии как привилегированной.
2. Редактор отправляет форму названия, описания и PDF. До изменения данных проверяются сессия, разрешение, CSRF token и ограничения запроса.
3. Приложение проверяет upload и сохраняет черновик. При ошибке форма показывает связанные с полями сообщения и сохраняет допустимые введённые значения; секреты и содержимое файла не отражаются в ошибке.
4. После успешного POST применяется redirect. Обновление страницы не повторяет создание. Защита от повторного upload/submit определяется для конкретного действия.
5. Публикация — отдельный POST с проверкой прав, CSRF и ожидаемого номера изменения. Новое состояние и успешное событие аудита фиксируются согласованно.
6. После commit обновляется публичное представление и применяется политика инвалидации, если cache включён. Редактор получает подтверждение фактического результата.
7. Снятие с публикации выполняется теми же механизмами проверки и фиксации изменения. Logout отзывает активную сессию, а не только удаляет cookie в браузере.

Для CSRF применяется документированный подход для cookie-authenticated форм, а не только SameSite cookie. Технический ориентир — [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). Публичные GET/HEAD не должны менять состояние документа.

## Согласованность БД и файлов

БД-транзакция не делает файловую систему частью того же commit. Первый вариант должен явно выбрать порядок операций и поведение при каждом сбое. Для локального диска предлагается следующий ограниченный протокол:

1. Получить файл в staging вне webroot, под случайным именем, с ограничением фактически прочитанных байтов. Проверить upload error, допустимый размер и серверный тип; вычислить hash.
2. Переместить проверенный файл в неизменяемый storage key. Для atomic rename staging и конечное хранилище размещаются на одной файловой системе; иначе потребуется другой протокол.
3. В одной БД-транзакции создать/изменить черновик, связать его с готовым файлом и записать успешное событие изменения. Ошибка commit оставляет невыдаваемый orphan, который может безопасно убрать отдельная процедура.
4. При публикации проверить текущую запись, готовность файла, разрешение и номер изменения; атомарно изменить состояние и добавить audit. До commit публичный запрос видит прежнее согласованное состояние.
5. Старый файл не удалять до успешного commit замены черновика. Неиспользуемые staging/orphan файлы удаляются по документированному правилу, которое не затрагивает действующие ссылки.

Этот протокол допускает временные orphan-файлы, но не допускает публикацию ссылки на ещё не готовый файл. Проверка наличия файла не отменяет необходимость backup/restore и защиты storage от посторонней записи. Другой backend, например object storage, потребует своего протокола; общий распределённый transaction manager здесь не предлагается.

Параллельные изменения не должны молча перезаписывать работу другого запроса. Обновление с устаревшим номером изменения отвергается как конфликт. Ошибка audit insert откатывает успешное изменение состояния в той же БД-транзакции. Диагностика неуспешного запроса записывается отдельно и не выдаётся за событие успешной публикации.

## Проверки файла и выдача

- В первой версии принимается ограниченный тип PDF; расширение и присланный MIME недостаточны. Сервер проверяет фактически полученный размер, тип и ошибки загрузки. Конкретные пределы задаются перед реализацией, без произвольных чисел в этом документе.
- Такая проверка не означает доказанную безвредность PDF. Необходимость антивируса или иной проверки зависит от модели эксплуатации и выбирается отдельно; файл не исполняется приложением и изначально выдаётся как вложение.
- Storage расположен вне `public`. Имена клиента не используются для путей; попытки traversal и управляющие символы не влияют на filesystem или headers.
- Download использует заранее проверенную запись, открывает допустимый storage key и передаёт поток. Размер памяти не растёт пропорционально полному размеру файла. Поведение при недоступном/повреждённом файле определено и диагностируется без раскрытия пути.
- `Content-Type`, `Content-Disposition` и политика кеша задаются явно. Поддержка Range не обещается автоматически; её необходимость и HTTP-поведение определяются отдельно.

## Публикация и кеш

Динамическая выдача из авторитетной БД — первый корректный вариант. При добавлении кеша разделяются публичные представления и защищённые ответы. Публикационная версия/поколение, если оно используется, изменяется в той же БД-транзакции, что и состояние документа; ключи и инвалидация опираются на этот результат.

Нельзя считать worker-local fallback общей инвалидацией. После commit сбой cache backend должен приводить к определённому безопасному пути: чтению актуальных данных или отказу соответствующего кешируемого пути, а не возврату закрытого содержимого. Если для этого потребуется durable invalidation/outbox, его вводят отдельной задачей вместе с тестом сбоя; для первого некешируемого каталога он не нужен.

Для HTTP-кеша задаются freshness, validators и варианты представления по [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html). Снятие с публикации прекращает новую выдачу приложением согласно выбранной политике. Уже скачанные копии и ранее разрешённый срок хранения у клиента нельзя объявить мгновенно отзывными. Поэтому политика долгого кеширования файла согласуется до её включения.

## Доступность и содержание

Технический ориентир примера — [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/). В приёмку входят последовательная структура страницы, понятные ссылки скачивания со сведениями о файле, клавиатура и видимый фокус, подписи полей, связанные ошибки и сообщения о результате. Проверяется полный процесс, включая вход и отказ отправки формы.

Доступность самого PDF и достоверность содержания принадлежат процессу подготовки документов приложения. Доступная HTML-карточка не делает автоматически доступным вложенный файл. Результат проверки примера не является заявлением о соответствии требованиям конкретного муниципального или государственного сайта.

## Приёмка по этапам

| Этап | Проверяемый результат |
| --- | --- |
| Публичное чтение | Список, карточка и потоковый download работают с БД без JavaScript и сессии; черновик/withdrawn не раскрываются; HTML-вывод безопасен; HEAD и ошибки согласованы; сохранены baseline и ручная проверка интерфейса |
| Редактор | Разрешённый пользователь проходит вход → upload → draft → publish; отсутствующие права/сессия/CSRF и недопустимый файл не меняют состояние; redirect предотвращает обычный повтор формы; конфликты выявляются явно |
| Согласованность | Искусственные сбои до/после перемещения файла, при записи БД и audit оставляют определённое восстанавливаемое состояние; orphan cleanup не удаляет действующие файлы |
| Публикация с кешем, если включён | После commit новая версия видна по выбранной политике; отказ backend и два независимых процесса не обходят состояние документа; условные запросы проверены вместе с 304 |
| Эксплуатация | Архив запускается на выбранной платформе; миграции приложения отделены от ядра; backup/restore восстанавливает БД и файлы согласованно; в логах нет секретов |

Интеграционные тесты используют изолированную тестовую БД, а файловые проверки — отдельный временный storage. Конкретные latency/memory budgets выбираются по baseline, а не заимствуются из старых k6 thresholds. Завершённость одного этапа не объявляет автоматически готовыми последующие.

## Что исключено из первого примера

Не входят поиск по содержимому PDF, OCR, редактор rich text, управление страницами сайта, многоступенчатое согласование, публикация по расписанию, импорт государственных реестров, юридически значимая подпись, публичные обращения граждан и хранение их персональных данных. Пример также не требует статического экспорта, CDN, очереди задач, SPA или отдельной frontend-сборки. Добавление такого сценария потребует собственной постановки, а не расширения `Platform` по умолчанию.
