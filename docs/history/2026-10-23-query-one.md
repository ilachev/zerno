## Result and integration

Storage gained queryOne: unchanged SQL, one PDO fetch, closeCursor in finally. SqlExecutor.fetchOne delegates and fetchOneRow maps one row. Catalog primary-key lookup uses the same SQL. No new services, flags, rewriting, or ORM are needed.

First-row/null semantics remain; there is no uniqueness check, added LIMIT, or reduction in RETURNING mutations. Failures preserve StorageException/PDOException/SQLSTATE. Custom implementations must add queryOne; no fetchAll fallback exists. Connections/statements are reused; reads are impure for PHPStan.

The direct caller avoids unpacking a list and typed execution shares the path. Other query/execute paths remain. Already-small results have no promised speed gain.

## CLI measurement

PHP 8.5.9, PostgreSQL 16.15 in an existing Docker image, Darwin arm64. A random schema held 20,000 rows with BIGINT key and 1,024-byte TEXT. Native buffered PDO was used. Each variant ran seven separate processes with one prepared warmup/read; forty-two processes were shuffled with seed 20261023. Paired SQL/first-row results were identical.

Legacy means fetchAll then rows[0]; one means queryOne. Memory was sampled after warmup before assertions/JSON against baseline. Both retained only the first row, so the comparison concerns temporary array peak.

| SQL case | Peak PHP bytes, legacy / one | Median call ms, legacy / one |
| --- | ---: | ---: |
| Primary-key lookup | 1,872 / 1,656 | 0.246 / 0.222 |
| ORDER BY LIMIT 1 | 1,872 / 1,656 | 0.290 / 0.301 |
| ORDER BY, no LIMIT, 20,000 rows | 33,648,440 / 1,656 | 42.225 / 24.969 |

These are short local observations, not HTTP latency predictions. Small timing differences establish no lookup advantage. The supported resource result is avoiding a large Zend array; PostgreSQL/native buffering may still obtain the whole result.

[pdo_pgsql cursor cleanup](https://github.com/php/php-src/blob/PHP-8.5/ext/pdo_pgsql/pgsql_statement.c) does not itself clear a cached PGresult. Lifetime follows statement reexecution/destruction. PHP counters exclude libpq/RSS/database/network; they do not establish full bounded memory or endurance. Use explicit LIMIT/unique predicates and field bounds.

## Reproduce

Prepare separate TEST_DB_* as in [infrastructure](../development/infrastructure-and-testing.md), then extract the recorded scripts:

```bash
mkdir -p var
python3 - <<'PY'
import json, pathlib
report = json.loads(pathlib.Path('docs/history/2026-10-23-query-one.json').read_text())
pathlib.Path('var/fetch-one-probe.php').write_text(report['probe_php'])
pathlib.Path('var/measure-fetch-one.py').write_text(report['runner_python'])
PY
python3 var/measure-fetch-one.py
```

The runner owns/cleans its random schema in finally, uses installed PHP/Python, and downloads nothing. It emits summaries and var/fetch-one-measurements.json. New measurements can differ.
