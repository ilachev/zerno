# Дорожная карта развития

Тип: `roadmap`. Статус: `accepted-plan`. Сверено с кодом: 2026-10-18.

## Как читать карту

Продуктовые границы заданы в [назначении проекта](./vision.md), обязательные цели — в [принципах развития](./principles.md), работающее устройство — в [архитектурном обзоре](../architecture/overview.md). Ниже для каждого направления отделены проверенная исходная база, предлагаемый результат и условия приёмки. Указанный владелец — слой архитектуры, а не назначенный человек.

Проверенная база и очередь core-задач находятся в конце документа. Векторы не являются шестью параллельными большими подсистемами. Не следует создавать абстракцию заранее только потому, что она упомянута в карте. Сначала нужен ограниченный сценарий и наблюдаемая проблема, затем минимальный общий контракт.

**Активный фокус — core-функции.** Каталог остаётся потребителем и стендом проверки. Его работающий публичный этап выявил потребности общего API; редактор, прикладные роли и публикационный workflow не являются следующей итерацией. Подключаемые механизмы ядра сохраняют явную композицию и не добавляются автоматически в минимальный pipeline.

Очередь следует [собственной модели разработки](vision.md#собственная-модель-разработки). Для каждой новой core-возможности нужны небольшой самостоятельный контракт, короткий код подключения, видимый путь исполнения и обоснование цены по сравнению с прямой сборкой существующих примитивов. Полнота набора подсистем и сходство с API другого фреймворка не служат критериями завершённости.

## Результаты по трём обязательным целям

Максимальная простота, максимальная полезная функциональность и максимальная производительность рассматриваются вместе. Матрица конкретизирует эти цели для планируемых результатов; она не объявляет их уже достигнутыми. Польза значимого изменения и его издержки по трём осям объясняются вместе с результатом, по [общим принципам](./principles.md).

| Направление | Простота использования и сопровождения | Полезная функциональность | Измеримая производительность |
| --- | --- | --- | --- |
| HTTP и runtime | Один явный путь request → handler → response; небольшой воспроизводимый запуск | Корректные методы, статусы, заголовки и тела в используемых сценариях | Сначала малый JSON/SELECT baseline, затем стоимость реальных HTML и файлов |
| HTML, формы и файлы | Обработчик, данные и шаблон без обязательных DSL и frontend-сборки | Нейтральные ответы, представление ошибок, обработка ввода и файлов, проверенные конкретными потребителями | Ограниченная страница результатов и выдача файла без скрытого полного чтения |
| Данные | Явный SQL, параметры, транзакции и небольшой контракт typed queries | Нужные приложению запросы и миграции, проверяемые конфликты и восстановление | Ограниченные результаты, понятное число SQL-вызовов, индексы под реальные запросы |
| Защищённый раздел | Явная композиция механизмов; прикладные права рядом с действиями | Вход, CSRF, разрешения и согласованный аудит в одном рабочем потоке | Публичные маршруты не запускают неподключённые session/auth механизмы; стоимость защиты измеряется без её отключения |
| Публикация и кеш | Сначала корректная динамическая выдача, дополнительные backend только по потребности | Публикация и снятие, определённая свежесть, условные запросы при их добавлении | Кеш добавляется ради измеренной пользы, с проверяемыми затратами на версии и инвалидацию |
| Эксплуатация | Единый PHP runner, явная конфигурация и отсутствие installer | Повторяемые запуск, проверки, сборка, восстановление и обновление | Runtime без devtools; наблюдаемая стоимость запуска и длительной работы |

Неподключённая optional-возможность не должна выполнять своё прикладное поведение при обычном запросе; стоимость общей загрузки учитывается отдельно по принципам. Автономная фиксированная поставка и работа с БД остаются основой; универсальное назначение ядра не ограничивается первым примером каталога.

## 1. Производительность и корректность HTTP

**Текущая база.** [App](../../src/Platform/Runtime/App.php) получает общий `RequestHandler`, а [RoadRunnerRuntime](../../src/Platform/Runtime/RoadRunnerRuntime.php) владеет worker loop. [SapiRequestFactory](../../src/Platform/Runtime/SapiRequestFactory.php) переводит globals, формы и uploads в request; [SapiResponseEmitter](../../src/Platform/Runtime/SapiResponseEmitter.php) передаёт заголовки, читает тело частями и исключает его для HEAD и соответствующих статусов. [Минимальная конфигурация](../../config/core.php) и [маршруты](../../config/routes.php) содержат только GET/HEAD `/health`. Есть unit и integration проверки [core-композиции](../../tests/Unit/Platform/Runtime/CoreApplicationTest.php).

Начальная итерация реализована: исправлены literal patterns, выбор метода и 405/`Allow`. Затем добавлен общий [ErrorResponse](../architecture/request-lifecycle.md#представление-http-ошибок): JSON по умолчанию, HTML через явную привязку; каталог больше не заменяет core pipeline и не преобразует JSON-ошибки. [Wire checker](../../tools/check-http.php) теперь выполняет 27 случаев с каждым представлением на каждом выбранном настоящем FPM/RR, включая generic 500 и HEAD. [Малый baseline](../development/http-and-baseline.md) содержит JSON без БД и один indexed SELECT, общую Caddy front-конфигурацию и изолированную PostgreSQL fixture. Условия начального замера сохранены в [отчёте](../history/2026-10-17-core-http-baseline.md); ускорение новой error-итерации не измерялось.

Прежние [k6-сценарии](../../load-tests/scenarios/) обращаются к отсутствующему маршруту и содержат исторические пороги. Они не используются новым baseline и не задают цель производительности.

**Файловая итерация реализована.** Общий [AttachmentResponse и прозрачная диагностика](../architecture/request-lifecycle.md#файловый-attachment-и-владение-потоком) проверяются с подключённым логированием на настоящих FPM/RR. Контракт, сопоставимый замер и границы памяти описаны в [отчёте](../history/2026-10-18-file-responses.md). Автоматическая content negotiation, замена router и новый слой шаблонизации для неё не требуются.

**Критерии приёмки.**

- Начальный набор уже проверяет статические и параметризованные маршруты, literal regex-символы, методы, 404/405 с `Allow`, HEAD, 204/304, повторные headers и URI/query. Он не является полной HTTP-матрицей; формы и ограничения входа добавляются по мере появления сценариев.
- Для JSON/SELECT сохранены команды, данные, задержки, ошибки, CPU и RSS процессов; SQL/request 0/1 указан по устройству handlers, без внешнего SQL tracer. Замеры HTML, файлов, соединений и длительного изменения памяти расширяются на работающем примере.
- FPM и RoadRunner сравниваются с одинаковой прикладной работой; генерация тестовых данных и вспомогательные сервисы не включаются скрытно только в один вариант. Выбор основного runtime остаётся открытым.
- Числовые бюджеты определяются по baseline. Изменение признаётся ускорением только при сопоставимых результатах и сохранённой корректности.

**Граница и зависимости.** HTTP-контракты и adapters принадлежат ядру; параметры сервера и стенда — эксплуатации; нагрузка каталога — примеру. После короткой начальной итерации разработка полезного сценария и его измерения идут вместе. Замена HTTP-библиотеки, переписывание router или выбор основного runtime заранее не требуются.

## 2. HTML, формы и файлы

**Текущая база.** Общие HTTP handlers и PSR-7/17 используются [публичным каталогом](../../examples/document-catalog/README.md): ограниченный список, карточка, download, HTML-ошибки и PHP-шаблоны без JavaScript/сессий. SQL ограничен на сервере, файлы находятся вне public. Общая система форм и редактор пока не реализованы; Html и файловая политика принадлежат примеру.

Потоковый SAPI emitter не гарантирует ограниченную память любого pipeline. Каталог явно включает RR chunk 8192 для seekable files; остальные профили сохраняют default 0 и полное чтение body. HttpLogging теперь пишет только metadata и сохраняет содержимое/позицию body; подключённое логирование включено в файловую wire-проверку. Это не гарантия ограниченной памяти default RR или любого остального middleware.

**Файловый результат реализован.** Общий AttachmentResponse создаёт attachment с безопасным Content-Disposition и готовым потоком без чтения payload; HTTP-диагностика не читает и не перемещает body. Потребитель — существующий DownloadHandler, проверки — SAPI/RR с логированием. Document, published-проверка, opaque storage key, PDF-only и cache policy остаются в приложении. Небольшие HTML-средства выделяются по конкретному использованию; общая система шаблонов или media manager не нужны. Затем отдельно развиваются ввод/валидация/формы, без обязательного редактора каталога.

**Критерии приёмки.**

- Первый публичный этап [каталога документов](./document-catalog-example.md) работает без JavaScript, входа и создания сессии: список, карточка и скачивание.
- Пользовательский текст безопасно отображается в выбранном HTML-контексте; невалидные идентификаторы и отсутствующие записи имеют определённый HTTP-результат. Контекст URL или JavaScript не считается защищённым обычным HTML-экранированием.
- При добавлении форм ошибки связываются с полями; обновление страницы после успешного redirect не повторяет запись. Защита от повторной отправки самого POST определяется для конкретного действия; политика защиты изменяющих запросов согласована с вектором 4.
- Проверяются размер и ошибки upload, серверный тип файла, безопасные имена и расположение вне `public`; случайные storage keys отделены от клиентского имени. Ограничения задаёт приложение.
- Скачивание проверяется end-to-end на каждом заявленном runtime: от handler через middleware до FPM/SAPI либо RR transport. Замер с разными размерами файла выявляет полную материализацию body; логирование не читает всё содержимое ради диагностики и не повреждает выдачу.
- Пример проходит ручную проверку клавиатуры, видимости фокуса, подписей и сообщений об ошибках. План проверки по [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/) ведётся по применимым критериям; набор автоматических тестов не считается полной оценкой доступности.

**Граница и зависимости.** Нейтральные HTML/HTTP-средства могут войти в ядро после подтверждения общего контракта. Шаблоны страниц, поля, внешний вид, PDF-only политика и каталог — приложение. Большой form builder, собственный язык шаблонов и медиа-менеджер в первый этап не входят. Upload редактора зависит от вектора 4; публичное чтение — только от HTTP и данных.

## 3. Данные и типизированный SQL

**Текущая база.** [Storage](../../src/Platform/Storage/Storage.php) предоставляет явный SQL с параметрами и транзакции; есть [PostgreSQL](../../src/Platform/Storage/PostgreSQLStorage.php) и [SQLite](../../src/Platform/Storage/SQLiteStorage.php) adapters. [SqlExecutor](../../src/Platform/Storage/Sql/SqlExecutor.php) исполняет типизированные queries. [sql-gen](../../tools/sql-gen/README.md) строит артефакты по SQL и schema, поддерживает ограниченный SQL subset, включая UPDATE, и проверяет PostgreSQL statements. [MigrationService](../../src/Platform/Storage/Migration/MigrationService.php) исполняет миграции; core использует отдельный пустой [каталог приложения](../../src/Migrations/). Изолированные PostgreSQL-схемы проверяют prepared parameters, commit/rollback и минимальную композицию в [integration tests](../../tests/Integration/Runtime/CoreApplicationTest.php).

Текущий [SQL subset](../../tools/sql-gen/src/Parser/grammar/sql_subset.pp2) не поддерживает `LIMIT`, а `SqlExecutor::fetchOne()` получает результаты через `Storage::query()`/`fetchAll()`: marker `:one` не ограничивает работу запроса. Известное ограничение вывода nullable для outer JOIN описано в [контракте генератора](../design/sql-gen-product.md). Миграции сейчас разделяются `explode(';')` и не получают общей атомарности DDL автоматически.

**Предлагаемый результат.** Публичный каталог уже использует прикладную миграцию и явный параметризованный SQL; typed generation можно подключить после подтверждённой потребности. До редактора проверить сбои/восстановление миграций и конкурирующие изменения. Развивать generator по конкретным запросам, не по попытке поддержать весь SQL.

**Критерии приёмки.**

- До публичного списка выбран короткий корректный путь: прямой подготовленный SQL с серверным ограничением либо целевое расширение grammar для пагинации с тестами. Число выбранных строк ограничено, порядок устойчив, число запросов не растёт на каждую запись; неизвестный ввод не превращается в SQL fragment.
- Generated artifacts синхронизируются с SQL и проходят static analysis; неподдерживаемый subset отвергается понятной ошибкой.
- До расширения выражений в generator исправляется nullable inference outer JOIN либо такая неподдержанная конструкция явно отвергается. Первый каталог может обойтись без outer JOIN; это не требует общей потоковой DB API.
- Ошибка записи откатывает прикладную операцию; конфликт одновременного изменения выявляется явно. Инварианты публикации и audit проверяются в одной БД-транзакции.
- До редакторского этапа проверены сбой миграции, повторный запуск и восстановление для нужного приложению SQL/DB profile. Миграция с ошибкой не объявляется успешной; `explode(';')` и отсутствие общей транзакции учитываются явно. Текущий API не обещает атомарности любого DDL или вложенных транзакций.
- В документации указана проверенная матрица PostgreSQL/SQLite. Наличие двух adapters не означает автоматической переносимости любого SQL, одинаковой конкурентности или одинаковой готовности к эксплуатации.

**Граница и зависимости.** PDO, транзакции, миграции и typed SQL contracts — ядро; generator — отдельный инструмент; schema и queries каталога — приложение. Интеграционные проверки выполняются на настоящей БД по [каноническому профилю](../development/infrastructure-and-testing.md). ORM, identity map и универсальный repository framework не требуются. План генератора уточняется в [sql-gen product design](../design/sql-gen-product.md).

## 4. Вход, CSRF, права и аудит действий

**Текущая база.** Отдельная [Session capability](../../src/Capabilities/Session/SessionModule.php) хранит сессии в БД. [SessionService](../../src/Capabilities/Session/Domain/SessionService.php) проверяет срок действия, обновляет и удаляет сессии; [SQL repository](../../src/Capabilities/Session/Infrastructure/Persistence/SqlSessionRepository.php) использует UPDATE-only refresh. [Регрессия отзыва](../../tests/Integration/Session/SessionRevocationTest.php) проверяет важные гонки удаления. Fingerprint не восстанавливает пользовательскую идентичность. Core-композиция эту capability не включает. Готового входа по учётным данным, CSRF, прикладной авторизации и журнала редакционных изменений нет; ApiStats учитывает HTTP-вызовы и не заменяет такой журнал.

**Предлагаемый результат.** Опциональная композиция для небольшого защищённого раздела: получение аутентифицированного субъекта, завершение/отзыв сессии, защита изменяющих запросов, явная проверка разрешения на действие и audit события. Конкретный способ получения учётной записи выбирается до реализации. Начальный пример не требует универсальной RBAC-схемы или SSO.

**Критерии приёмки.**

- Анонимный запрос, пользователь без разрешения и отозванная сессия не меняют данные и не получают закрытый файл. Проверка выполняется сервером для каждого защищённого действия.
- Вход и смена уровня доступа исключают фиксацию старой сессии; logout и административный отзыв действуют между процессами. Настройки cookie и HTTPS-профиля проверяются отдельно от существующих defaults.
- Изменяющие cookie-authenticated запросы без корректной CSRF-защиты отвергаются до записи. SameSite не принимается за единственный механизм; выбранный подход и исключения документируются с опорой на [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).
- Успешное изменение и прикладное событие аудита фиксируются согласованно; audit содержит субъекта, действие, объект и время, но не пароль, session secret или CSRF token. Неуспешные попытки имеют отдельно определённый диагностический путь.
- Тесты охватывают разрешённые и запрещённые действия, повторную отправку и гонку отзыва. Ограничение попыток входа и сценарий восстановления доступа определены до использования редакторского раздела.

**Граница и зависимости.** Механизмы сессий/входа, CSRF и передачи identity — опциональный набор; словарь прав, назначение ролей и содержание audit — приложение. HTTP и транзакции — ядро. Зависит от векторов 1–3. MFA, SSO, электронные подписи и специальные криптографические интеграции требуют самостоятельных решений.

## 5. Публикация и кеширование

**Текущая база.** Есть [CacheService](../../src/Platform/Cache/CacheService.php), scopes и [RoadRunner backend](../../src/Platform/Cache/RoadRunnerCacheService.php) с fallback. Они не включены в core и не образуют систему публикации. Нет общей реализации HTTP validators, публикационных версий или статического экспорта. Сессии читают авторитетную БД, а не локальный fallback cache.

**Предлагаемый результат.** Начать с корректной динамической выдачи опубликованных данных. Затем добавить явную политику HTTP-кеша и, только при измеренной пользе, кеш представлений. У публикации должен быть проверяемый переход состояния и способ согласовать его с кешами всех процессов. [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html) служит технической основой для freshness, revalidation и shared cache policy.

**Критерии приёмки.**

- Черновик и закрытые ответы не попадают в публичный cache. Публичное чтение не создаёт сессию. Cache key учитывает реально используемые варианты представления.
- После commit публикации новая версия становится доступна по определённому правилу. Ошибка backend или worker-local fallback не может вернуть черновик или обойти проверку доступа.
- При добавлении HTTP validators ETag/Last-Modified и условные запросы проверяются вместе с 304 и его заголовками. Если включён server-side cache, согласованность и инвалидация проверяются минимум между двумя процессами, включая локальный fallback. Для первой динамической публикации эти механизмы не обязательны.
- Для снятия с публикации описаны прекращение новой выдачи, допустимая задержка включённых кешей и восстановление после сбоя. Уже скачанные копии не объявляются отзывными.
- До включения кеша есть baseline и тест без него. При отказе необязательного кеша сохраняется определённое корректное поведение.

**Граница и зависимости.** HTTP-примитивы могут быть общими; backend — adapter; состояния, публикационная версия, область инвалидации и допустимая устарелость — приложение. Зависит от данных и прав редактора. Статический export, CDN и очередь публикаций не обязательны для первой версии; они вводятся отдельной задачей после явного сценария отказов.

## 6. Эксплуатация и обновление поставки

**Текущая база.** [PHP command runner](../../tools/project.php) запускает gates и сборку без установки пакетов; [integrity checker](../../tools/check-third-party.php) проверяет фиксированную поставку. Есть [CI](../../.github/workflows/ci.yml), [release workflow](../../.github/workflows/release.yml), runtime-only archive, отдельные test DB settings и случайные схемы. [Архитектура поставки](../design/autonomous-core.md) описывает текущие bootstrap/distributions и ограничения provenance; [исторический аудит](../history/2026-10-17-autonomy-audit.md) фиксирует прежний запуск без Composer и внешней сети. Существуют logger/request ID и migration CLI. Это база поставки, а не завершённая система обновления работающего сайта.

**Предлагаемый результат.** Воспроизводимая установка приложения из архива на выбранной платформе; документированные конфигурация, секреты, права каталогов, запуск, остановка, миграции, резервное копирование и восстановление. Отдельно — управляемое обновление включённого стороннего кода с сохранением происхождения, notices, локальных patches и проверок.

**Критерии приёмки.**

- Чистый checkout проходит канонический gate без менеджера пакетов; runtime-архив запускается без generator/devtool distributions. Проверяются manifest и отсутствие незаявленных файлов.
- Оператор может воспроизвести backup и restore БД вместе с файлами приложения; восстановленный каталог выдаёт согласованные записи и содержимое. Cache не является единственной копией данных.
- Путь обновления описывает порядок остановки/перезапуска, миграции, проверку readiness и восстановление при сбое. Откат кода не объявляется автоматическим откатом необратимых изменений данных.
- В логах есть связь по request ID и причина сбоя без секретов; health без БД отделён от проверки готовности зависимостей, если такая readiness вводится.
- Обновление стороннего компонента оставляет проверяемый diff, версию/ref, происхождение, license notices и новые hashes; затем проходит функциональные и необходимые сравнительные проверки.

**Граница и зависимости.** Формат поставки и нейтральная диагностика — проект; параметры серверов и backup — эксплуатационный профиль; секреты, retention и обслуживание данных — владелец приложения. Политика версий, срок поддержки, лицензия собственного кода и доверие к подписи будущих релизов пока открыты. Текущие команды не заменяются здесь новыми: их источник — [инфраструктура и тестирование](../development/infrastructure-and-testing.md).

## Адресные зависимости дополнительных возможностей

[HttpRequestOptions](../../src/Platform/Http/Client/HttpRequestOptions.php) по умолчанию задаёт `idempotent=true`, а [resilient client](../../src/Platform/Http/Client/ResilientHttpClient.php) использует этот признак для retries. До применения клиента к изменяющим внешним операциям нужна безопасная политика повторов и проверка POST/сбоев. Это не блокирует core-каталог без исходящих интеграций.

Ограничение SQL-результата нужно до списка, end-to-end проверка выдачи — до обещания ограниченной памяти файла, а проверка восстановления миграций — до редактора. Остальные ограничения закрываются при использовании соответствующей возможности; вся работа не переносится в начальную HTTP-итерацию.

## Проверенная база и очередь core-задач

Завершены HTTP routing/wire-итерация и публичный контрольный пример: результаты сохранены в [JSON/SELECT baseline](../history/2026-10-17-core-http-baseline.md) и [отчёте каталога](../history/2026-10-17-public-catalog.md). Следом реализован общий [ErrorResponse](../architecture/request-lifecycle.md#представление-http-ошибок), проверенный на default JSON и HTML-потребителе с сохранением 404/405/500, Allow, HEAD и границ ошибок. Это база проверки, а не очередь развития прикладного продукта. Локальные Html/FileStore/Errors остаются кодом примера, HTML Errors реализует общий контракт.

| Очередь | Ограниченный результат ядра | Потребитель и критерий выхода |
| --- | --- | --- |
| 1. Файловый ответ и прозрачная диагностика — реализовано | [AttachmentResponse](../architecture/request-lifecycle.md#файловый-attachment-и-владение-потоком), безопасные headers и metadata-only logging | DownloadHandler сохраняет прикладную политику; [проверены](../history/2026-10-18-file-responses.md) логирование, SAPI/RR, размеры/хеши, закрытие streams и ограниченная память выбранного пути |
| 2. Ограниченные SQL-результаты и надёжность БД | Целевая поддержка LIMIT в существующем typed SQL subset; определённый контракт fetchOne, проверки ошибок транзакций/миграций отдельными небольшими задачами | Запрос списка и lookup уже существуют; явный SQL сохранён, реальные PostgreSQL checks подтверждают границы чтения и восстановление. ORM, pagination DSL и общая streaming DB API не требуются |
| 3. Ввод, валидация и формы | Небольшие нейтральные средства разбора/ограничения ввода, ошибок полей, redirect и безопасного upload | Минимальный проверочный сценарий использует общий API; он не требует расширять каталог редакторскими сущностями и workflow |
| 4. Подключаемая защита и эксплуатация | Явные механизмы session/CSRF/identity там, где нужен защищённый сценарий; измерения длительной работы и проверяемое обновление | Публичный путь не получает лишних обращений; конкретная identity и прикладные права выбираются отдельно, проверки отказов соответствуют включённой возможности |

Каждая строка задаёт направление для ограниченных изменений, а не одну большую подсистему. Для очередной итерации выбирается один подтверждённый общий контракт, конкретный потребитель и проверки по трём целям. Числовые бюджеты и основной runtime остаются открытыми. [Дизайн редактора каталога](./document-catalog-example.md) сохраняется как отложенный сценарий; автоматически продолжать его после публичного чтения не следует.

## Отложенные расширения

- Общие CMS/workflow/form-builder системы и собственный язык шаблонов — до подтверждённой потребности нескольких сценариев.
- Статический export, CDN, распределённый cache и durable outbox — до задачи, которую не решает простой динамический путь.
- SSO/MFA, подписи и внешние изменяющие интеграции — после выбора конкретной модели identity и безопасных правил повторов.
- Полный SQL parser, общая streaming DB API и глубокая переносимость dialect — по реальным запросам, а не ради полноты инструмента.
- Широкий benchmark-контур и смена runtime/HTTP-библиотек — по результатам полезных сценариев; короткие замеры сопровождают работу с первой итерации.
