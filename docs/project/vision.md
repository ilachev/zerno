# Назначение и границы проекта

Тип: `design`. Статус: `accepted-plan`. Сверено с кодом: 2026-10-18.

## Для кого создаётся проект

«Зерно» (`zerno`) развивается в небольшое универсальное автономное PHP HTTP/PDO-ядро для разработчиков веб-приложений. Разработчики муниципальных и государственных сайтов — одна из приоритетных аудиторий; это ориентир для полезных сценариев, а не ограничение назначения ядра. Публичные страницы, документы, формы и защищённые рабочие разделы нужны разным приложениям. Разработчик должен получить понятный путь от HTTP-запроса через явный обработчик и SQL до HTML-ответа, без обязательного большого framework или CMS.

Название отражает небольшую основу, из которой вырастает конкретное приложение.

Первый продукт — основа для разработки, а не готовое прикладное решение. Структура разделов, редакционная политика, оформление, роли пользователей и интеграции принадлежат конкретному приложению. Предполагаемый способ проверить пригодность основы — небольшое [приложение каталога документов](./document-catalog-example.md), отделённое от `Platform`.

Текущее состояние кода описывает [архитектурный обзор](../architecture/overview.md). Этот документ объясняет, зачем развивать проект; он не заменяет описание работающих компонентов или инструкции из корневого `AGENTS.md`.

## Обязательные цели развития

Максимальная простота, максимальная полезная функциональность и максимальная производительность применяются совместно. Путь разработчика, покрытые сценарии и стоимость исполнения оцениваются для каждого значимого изменения. Корректность и сохранность данных остаются условиями сравнения. Канонические определения, работа с компромиссами и правила для агентов находятся в [принципах развития](principles.md); здесь задаются продуктовые границы.

## Принятые ориентиры

### Собственная модель разработки

Отличительный подход «Зерна» — небольшая автономная основа, из которой разработчик собирает приложение обычным PHP и сохраняет контроль над исполнением и данными. Направление продукта определяется этой моделью и тремя целями, а не воспроизведением API или перечня подсистем другого фреймворка.

| Свойство модели | Что получает разработчик | Чем подтверждать |
| --- | --- | --- |
| Автономная поставка | Исходники и фиксированные инструменты уже доступны; установка пакетов не входит в путь запуска или проверки | Checkout, генерация, gates и runtime-архив работают при наличии документированной платформы |
| Прослеживаемое исполнение | Путь маршрут → handler → SQL/поток → ответ можно восстановить по обычному коду и конфигурации | Явные зависимости и время жизни; проверка startup/request I/O выбранного профиля |
| SQL как исходник | Запросы, лимиты и транзакции остаются видимыми; необязательная типизация готовится до runtime | SQL inputs и план PostgreSQL доступны; генератор не нужен обслуживающему процессу |
| Самостоятельные механизмы | Общий блок решает конкретную задачу и подключается без обязательной иерархии слоёв | Короткий пример использования, конкретный потребитель и проверенная цена подключения |

Самостоятельность подхода сохраняет совместимость с HTTP, PDO, PSR и полезными включёнными компонентами. Новые механизмы оцениваются по понятности использования, полезным сценариям и измерениям; непривычный синтаксис или число собственных классов не являются результатом. Текущее состояние описывает [архитектура](../architecture/overview.md), правила проектирования — [принципы](principles.md).

### Небольшая основа с полноценной работой с БД

HTTP, маршруты, обработчики, конфигурация, базовая диагностика и работа с БД входят в основу. PDO, подготовленные запросы, явный SQL, транзакции и миграции — обычные возможности ядра. Отсутствие SQL на конкретном маршруте означает ленивое получение соединения, а не исключение БД из продукта.

Типизированная SQL-генерация сохраняет SQL исходником запроса. Её назначение — проверять параметры и результаты до runtime, не превращая persistence в ORM или обязательный query builder. Подробности и отдельные границы генератора находятся в [плане sql-gen](../design/sql-gen-product.md).

### Автономная фиксированная поставка

Для запуска, разработки, проверки и сборки не нужен менеджер PHP-пакетов или этап установки зависимостей. Выбранные сторонние исходники и инструменты включаются в репозиторий с фиксированными версиями, происхождением, notices и проверяемыми хешами. Использование небольшого стороннего кода допустимо; переименование библиотеки или её скрытое копирование не делает её собственным кодом проекта.

Текущая поставка разделяет runtime, зависимости генераторов и инструменты качества. Runtime-архив содержит только свой контур. Генераторы и quality tools работают из исходного репозитория отдельными процессами. Состав поставки и ограничения происхождения снимков описаны в [архитектуре автономной поставки](../design/autonomous-core.md); команды — в [инфраструктуре и тестировании](../development/infrastructure-and-testing.md).

PHP, его расширения, выбранная СУБД, веб-сервер, необязательный RoadRunner и компиляторы контрактов являются требованиями платформы. Их наличие и версии проверяются отдельно от включённых PHP-исходников. Автономная поставка не означает наличие собственного интерпретатора PHP, сервера БД или исполняемого `protoc` в runtime-архиве.

### Серверный HTML как основной веб-сценарий

Разработчик должен иметь возможность создать обычный серверный сайт: отдать HTML, обработать форму, сохранить данные и выдать файл. JavaScript дополняет такой сценарий по необходимости. Обязательная SPA, Node.js-сборка или protobuf-контракт для каждого маршрута в это направление не входят.

Существующая protobuf API-композиция сохраняется как отдельная возможность. Её transport contracts и генерация не определяют обязательное устройство HTML-приложения. [Protobuf и codegen](../architecture/protobuf-and-codegen.md) описывают этот отдельный контур.

### Производительность через измерения

Приоритет — минимальные оправданные затраты PHP на полезную работу приложения: обработку HTTP, HTML и БД. Изменения сравниваются на одинаковом поведении и наборе данных. Учитываются задержки, CPU, память процессов, обращения к БД, соединения и ошибки, а для worker — ещё состояние при длительной работе.

Первичный runtime, числовые бюджеты задержек и памяти пока не выбраны. Наличие FPM и RoadRunner adapters позволяет сравнить одну прикладную логику в разных моделях исполнения. Нельзя объявлять ускорение по тесту `/health`, переносить результат одного стенда на все сайты или выбирать архитектуру по выдуманному RPS.

### Доступность как проверяемая техническая цель

Для HTML-примеров и будущих повторно используемых элементов интерфейса выбран технический ориентир [WCAG 2.2 уровня AA](https://www.w3.org/TR/WCAG22/). Проверка охватывает пользовательский процесс целиком и сочетает автоматические и ручные проверки. Это цель разработки, а не заявление о выполненном аудите или юридическом соответствии конкретного сайта.

## Кто отвечает за поведение

| Слой | Его ответственность | Что не следует переносить сюда |
| --- | --- | --- |
| Ядро `Platform` | HTTP-контракты и adapters, маршрутизация, обработчики, конфигурация, PDO/SQL/транзакции/миграции, небольшие нейтральные средства диагностики | Типы муниципальных документов, структура сайта, роли сотрудников, редакционное согласование |
| Необязательные возможности и adapters | Сессии и будущая аутентификация, механизмы CSRF и проверки прав, cache backends, protobuf API, RoadRunner, внешние интеграции | Обязательное включение этих возможностей для публичного HTML или `/health` |
| Прикладной код | Страницы, формы, предметные правила, SQL приложения, допустимые файлы, права на действия, публикация и состав аудита | Изменение общих механизмов ради одного сайта без повторно используемой потребности |
| Примеры | Законченный небольшой сценарий, показывающий композицию механизмов | Скрытые зависимости ядра от примера или статус готовой CMS |

Некоторые низкоуровневые средства, например потоковый HTTP-ответ или экранирование текста, могут понадобиться разным приложениям. Их место определяется подтверждённым общим контрактом. Наличие такой потребности не означает необходимости общей системы форм, собственного языка шаблонов или универсального хранилища файлов.

## Что уже есть и что ещё предстоит

На дату проверки реализованы автономная PHP-поставка, общий `App`/`RequestHandler`, минимальная HTTP/PDO-композиция, SAPI и RoadRunner adapters, явные маршруты, PDO storage, типизированный SQL-контур и миграции. Минимальный `/health` не включает сессии, статистику, GeoIP и protobuf и не открывает БД. В отдельной API-композиции эти интеграции сохраняются.

Публичный HTML-каталог уже реализован как проверочный пример. Его Html/FileStore/Errors пока локальны приложению. Текущий приоритет — нейтральные HTTP, файловые и SQL-возможности по [дорожной карте](./roadmap.md). Общие формы, вход по учётным данным и CSRF остаются направлением развития; редакторский интерфейс, прикладные права, аудит действий и публикационный workflow отложены. Существующие Session и ApiStats capabilities не означают готовой системы доступа или аудита изменений.

## Открытые решения

| Вопрос | Что уже зафиксировано | Что ещё нужно решить |
| --- | --- | --- |
| Основной runtime | Одна логика приложения работает через SAPI и RoadRunner | Предпочтительный профиль эксплуатации после одинаковых замеров |
| Производительность | Нужны воспроизводимые сравнения и контроль памяти | Числовые бюджеты для конкретных сценариев и стенда |
| Поддержка платформ | Есть PostgreSQL и SQLite adapters; текущий профиль по умолчанию использует PostgreSQL | Точная матрица проверенных версий, обещаемая глубина поддержки каждого dialect |
| Собственный код и поддержка | Сторонние notices и происхождение сохраняются | Лицензия проекта, выпуск и срок поддержки версий, модель сопровождения |
| Идентификация и криптография | Безопасность должна опираться на поддерживаемые механизмы платформы и явные модели угроз | Источники учётных записей, MFA/SSO, требования конкретных интеграций, необходимость подписей и шифрования данных |
| Публикация | Динамический серверный HTML достаточен для первого приложения | Нужны ли CDN, отдельный cache backend или статический экспорт на следующем этапе |

Эти вопросы не считаются решёнными по названию класса, исторической настройке API или предложению в design-документе. В частности, проект не обещает собственную криптографию, государственные интеграции, сертификацию или исполнение требований законодательства без отдельной задачи и проверки.

## Что не строим в первой волне

Не планируются готовая CMS, конструктор страниц, универсальный workflow согласования, собственные ORM и язык шаблонов, обязательный frontend toolchain, мультиарендность или распределённая платформа. Статическая публикация остаётся возможным расширением. Действующий пример ограничен публичным чтением; защищённый поток редактирования — отложенный прикладной сценарий для будущей проверки механизмов ядра. Перечень последующих направлений не является разрешением реализовать их все одновременно.
