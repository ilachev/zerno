# Пример: публичный каталог документов

Тип: `design`. Статус: `accepted-plan`. Сверено с кодом: 2026-10-20.

## Задача и границы

Пример проверяет, достаточно ли небольшого универсального HTTP/PDO-ядра для полезного серверного сайта. Посетитель открывает список опубликованных документов, читает карточку и скачивает файл. Редактор, черновики и публикационный workflow описаны как отложенный прикладной сценарий. Активная очередь проекта развивает общие core-функции по [roadmap](roadmap.md); публичный каталог служит их потребителем и проверкой. Все основные действия доступны без JavaScript. Каталог полезен муниципальным и государственным сайтам, но не ограничивает этим применение ядра.

Публичный этап реализован в [`examples/document-catalog`](../../examples/document-catalog/README.md): отдельная конфигурация, маршруты, обработчики, PHP-шаблоны, явный SQL и миграция. Его bootstrap регистрирует собственный namespace только при подключении примера; исходники включены в runtime-архив. Ниже публичное чтение описывает реализованный контракт, а редактор, upload и публикационный workflow — отложенный план приложения. Проверки и измерения публичного этапа сохранены в [отчёте](../history/2026-10-17-public-catalog.md).

Пример следует [назначению проекта](./vision.md) и [обязательным принципам](./principles.md), использует [текущую архитектуру](../architecture/overview.md) и проверяет шаги из [дорожной карты](./roadmap.md). Команды запуска и проверки берутся из [инфраструктуры и тестирования](../development/infrastructure-and-testing.md); этот дизайн не добавляет фиктивных runnable-команд.

## Что пример должен дать разработчику

| Цель | Результат в примере |
| --- | --- |
| Максимальная простота | Понятный путь от маршрута через handler и SQL к HTML; немного обязательных настроек, без installer, обязательного protobuf или собственного языка форм/шаблонов |
| Максимальная полезная функциональность | Завершённые список → карточка → скачивание, затем вход → создание/редактирование черновика → публикация, собранные из небольших механизмов |
| Максимальная производительность | Ограниченная пагинация и SQL, потоковая выдача без скрытого полного чтения, отсутствие неподключённой auth/cache работы; стоимость измеряется на работающем сценарии |

Разработчик должен суметь проследить весь публичный путь по конфигурации маршрутов, обработчику, SQL и шаблону. Добавление поля или изменения представления не должно требовать правки `Platform`, generated PHP или настройки неиспользуемых интеграций. Миграции, данные примера и допустимые файлы описываются явно в приложении. Типизированная генерация, если используется, запускается из SQL-исходников включённым инструментом.

Защищённый этап расширяет эту же небольшую композицию: сессии, identity и проверки подключаются к границе редакторских действий, а публичные маршруты сохраняют свой простой путь. Это проектируемое поведение, не готовая возможность каталога. Перечень обязательных шагов запуска и понятий проверяется на самом примере вместе с его функциональностью и стоимостью.

## Самостоятельный первый этап: публичное чтение

Первый этап не зависит от реализации входа, CSRF, upload UI или универсального кеша. Ему предшествует короткая итерация подтверждённых HTTP-исправлений и JSON/SELECT baseline из [roadmap](./roadmap.md), а не завершение большого benchmark-стенда. Опубликованные записи и тестовые файлы создаются контролируемой fixture/import процедурой приложения. Нельзя добавлять публичный endpoint для их создания ради обхода ещё не готового редактора.

| Реализованный маршрут | Поведение |
| --- | --- |
| `GET /documents` | Ограниченный список опубликованных записей с устойчивым порядком и обычной навигацией страниц |
| `GET /documents/{id}` | HTML-карточка опубликованного документа: название, описание, дата публикации, сведения о файле и ссылка скачивания |
| `GET /documents/{id}/download` | Потоковая выдача файла после проверки состояния документа и связи с файлом |
| `HEAD` для этих ресурсов | Те же определённые метаданные ответа без выдачи тела |

Для отсутствующей, непубличной или некорректно указанной записи приложение возвращает HTML 404 без раскрытия черновика или storage path; некорректный `before` — HTML 400, неподдерживаемый метод — HTML 405 с Allow. Обычный публичный запрос не создаёт сессию и `Set-Cookie`. Контракты запуска, размера страницы и private storage уточняет README примера.

Для начала допустимо читать БД на каждом запросе без общего cache. Политика HTTP-кеширования задаётся явно; длительная публичная freshness не включается до согласования снятия с публикации. Такой этап уже позволяет измерить HTML, SQL и потоковую выдачу, проверить доступность и использовать пример как контроль при развитии общих механизмов ядра.

### Границы запроса и измерения после рабочего сценария

Пагинация ограничивает SQL-результат на сервере до его чтения в PHP; query parameter не может запросить весь каталог или неограниченный размер страницы. Выбирается простой способ навигации со стабильным порядком. Число запросов на страницу не растёт на каждую отображаемую запись; необходимость общего `COUNT` определяется интерфейсом.

Текущий [generator subset](../../tools/sql-gen/src/Parser/grammar/sql_subset.pp2) поддерживает `LIMIT`; сценарий ограниченного списка проверен отдельной PostgreSQL fixture. Каталог сохраняет три явных SQL constants в `CatalogRepository`: фиксированный LIMIT 21, keyset `id < :before`, ORDER BY id DESC и lookup по primary key. Собственная schema каталога и строковые literals не входят в текущий API profile генератора; граница описана в [контракте LIMIT](../design/sql-gen-product.md#ограниченная-select-выборка). Handler показывает 20 строк, дополнительная определяет ссылку следующей страницы. [SqlExecutor](../../src/Platform/Storage/Sql/SqlExecutor.php) по-прежнему получает массив через storage и `fetchAll()`, в том числе для `fetchOne()`. Общая потоковая DB API и outer JOIN с известным ограничением nullable inference этому сценарию не нужны.

После того как список, карточка и download работают, в той же итерации фиксируются простые воспроизводимые замеры:

| Сценарий | Что проверяется и измеряется |
| --- | --- |
| Страница списка | Фактический предел строк, порядок, число SQL-вызовов, задержка и память на выбранном наборе данных |
| Карточка | Ограниченный запрос метаданных; отсутствие дополнительных SQL-вызовов на каждое поле или скрытой session/auth работы |
| Скачивание | Размер переданного файла, память PHP и процесса/worker, задержка, стоимость определения размера/заголовков и поведение клиента на заявленном runtime |

Эти результаты дополняют малый JSON/SELECT baseline; они не требуют отдельной платформы benchmark-управления. Сначала сохраняются понятные команды, данные и наблюдаемая стоимость, затем выбирается конкретное улучшение. Числовые бюджеты не назначаются заранее, корректность и доступность сохраняются.

## Роли и разрешения следующего этапа

| Участник | Разрешённые действия |
| --- | --- |
| Посетитель | Читать и скачивать только опубликованное |
| Редактор | Создать и изменить черновик, загрузить допустимый файл, опубликовать и снять свою доступную запись с публикации согласно политике примера |
| Оператор | Подготовить конфигурацию и учётные записи, выполнить миграции, backup/restore и техническое обслуживание вне публичных routes |

Начальный пример может предоставить одному редактору весь этот ограниченный набор действий. Разделение автора и согласующего, сложная ролевая иерархия, делегирование и универсальная admin UI не нужны. Сервер всё равно проверяет конкретное разрешение и объект для каждого действия; скрытая кнопка не считается авторизацией.

Источник учётных записей выбирается до защищённого этапа. При локальных паролях понадобятся поддерживаемые средства PHP для хеширования/проверки, настройка стоимости, ограничение попыток и определённая процедура восстановления доступа. Дизайн не закрепляет SSO, MFA, внешнего identity provider или собственную криптографию.

До редактора проверяются миграции приложения при ошибке, повторном запуске и восстановлении: текущий [MigrationService](../../src/Platform/Storage/Migration/MigrationService.php) делит SQL через `explode(';')` и не обеспечивает атомарность произвольного DDL. Для выбранных миграций нужен определённый рабочий путь; общая переработка всего SQL-инструментария не является предварительным условием редактора.

## Состояния и данные

Текущая таблица `catalog_documents` содержит id, title, description, status, published_at, storage_key, original_name и file_size. `Document` переносит семь публичных полей без status, `CatalogRepository` выбирает только published. Seed создаёт PDF и использует SHA-256 содержимого как storage key; отдельного hash-поля и generated PHP-классов нет. Номер изменения для контроля конкуренции, дополнительные timestamps и upload metadata относятся к следующему редакторскому этапу.

| Состояние документа | Видимость и переходы |
| --- | --- |
| `draft` | Доступен разрешённому редактору; можно менять данные и вложение. Публикация разрешена только с готовым проверенным файлом |
| `published` | Появляется в публичных списке, карточке и download route. В первой версии содержимое и файл фиксируются; допускается снятие с публикации |
| `withdrawn` | Не выдаётся новым публичным запросам. Данные и audit сохраняются до отдельно определённого обслуживания |

Повторная публикация, замена уже опубликованного содержимого и редакционные версии требуют отдельного решения. Номер изменения для optimistic concurrency не следует автоматически считать полноценной историей версий. В первой реализации можно потребовать новый документ для новой публикации, не создавая общий workflow engine.

Все публичные SQL-запросы ограничены опубликованным состоянием. Download не получает произвольный file path из URL и не ограничивается проверкой существования blob. Закрытый файл не становится публичным из-за того, что его идентификатор угадан.

## Защищённый пользовательский поток

1. Редактор входит; identity и проверка разрешений подключаются только к соответствующей композиции. При входе исключается повторное использование прежней неаутентифицированной сессии как привилегированной.
2. Редактор отправляет форму названия, описания и PDF. До изменения данных проверяются сессия, разрешение, CSRF token и ограничения запроса.
3. Приложение проверяет upload и сохраняет черновик. При ошибке форма показывает связанные с полями сообщения и сохраняет допустимые введённые значения; секреты и содержимое файла не отражаются в ошибке.
4. После успешного POST применяется redirect. Обновление страницы не повторяет создание. Защита от повторного upload/submit определяется для конкретного действия.
5. Публикация — отдельный POST с проверкой прав, CSRF и ожидаемого номера изменения. Новое состояние и успешное событие аудита фиксируются согласованно.
6. После commit обновляется публичное представление и применяется политика инвалидации, если cache включён. Редактор получает подтверждение фактического результата.
7. Снятие с публикации выполняется теми же механизмами проверки и фиксации изменения. Logout отзывает активную сессию, а не только удаляет cookie в браузере.

Для CSRF применяется документированный подход для cookie-authenticated форм, а не только SameSite cookie. Технический ориентир — [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). Публичные GET/HEAD не должны менять состояние документа.

## Согласованность БД и файлов

БД-транзакция не делает файловую систему частью того же commit. Первый вариант должен явно выбрать порядок операций и поведение при каждом сбое. Для локального диска предлагается следующий ограниченный протокол:

1. Получить файл в staging вне webroot, под случайным именем, с ограничением фактически прочитанных байтов. Проверить upload error, допустимый размер и серверный тип; вычислить hash.
2. Переместить проверенный файл в неизменяемый storage key. Для atomic rename staging и конечное хранилище размещаются на одной файловой системе; иначе потребуется другой протокол.
3. В одной БД-транзакции создать/изменить черновик, связать его с готовым файлом и записать успешное событие изменения. Ошибка commit оставляет невыдаваемый orphan, который может безопасно убрать отдельная процедура.
4. При публикации проверить текущую запись, готовность файла, разрешение и номер изменения; атомарно изменить состояние и добавить audit. До commit публичный запрос видит прежнее согласованное состояние.
5. Старый файл не удалять до успешного commit замены черновика. Неиспользуемые staging/orphan файлы удаляются по документированному правилу, которое не затрагивает действующие ссылки.

Этот протокол допускает временные orphan-файлы, но не допускает публикацию ссылки на ещё не готовый файл. Проверка наличия файла не отменяет необходимость backup/restore и защиты storage от посторонней записи. Другой backend, например object storage, потребует своего протокола; общий распределённый transaction manager здесь не предлагается.

Параллельные изменения не должны молча перезаписывать работу другого запроса. Обновление с устаревшим номером изменения отвергается как конфликт. Ошибка audit insert откатывает успешное изменение состояния в той же БД-транзакции. Диагностика неуспешного запроса записывается отдельно и не выдаётся за событие успешной публикации.

## Проверки файла и выдача

- В первой версии принимается ограниченный тип PDF; расширение и присланный MIME недостаточны. Сервер проверяет фактически полученный размер, тип и ошибки загрузки. Конкретные пределы задаются перед реализацией, без произвольных чисел в этом документе.
- Такая проверка не означает доказанную безвредность PDF. Необходимость антивируса или иной проверки зависит от модели эксплуатации и выбирается отдельно; файл не исполняется приложением и изначально выдаётся как вложение.
- Storage расположен вне `public`. Имена клиента не используются для путей; попытки traversal и управляющие символы не влияют на filesystem или headers.
- Download использует заранее проверенную запись, открывает допустимый storage key и передаёт поток. Размер памяти не растёт пропорционально полному размеру файла. Поведение при недоступном/повреждённом файле определено и диагностируется без раскрытия пути.
- Ограниченная память проверяется на всём пути, а не только в handler: SAPI/FPM и RR отдельно. Каталог явно выбирает `RoadRunnerServiceProvider(chunkSize: 8192)` для seekable regular files. Default остальных профилей остаётся 0 с материализацией body; streaming path bundled библиотеки не поддерживает non-seekable body и informational 1xx. [HttpLoggingMiddleware](../../src/Platform/Http/Middleware/HttpLoggingMiddleware.php) пишет метаданные ответа без чтения body и сохраняет позицию потока; файловая выдача с подключённым логированием проверена на обоих runtime.
- Определение размера, headers и логирование не должны перечитывать всё содержимое на каждом скачивании. Измерение с разными размерами файла должно выявлять такие затраты; размер chunk, буферы сервера и память worker учитываются в end-to-end результате.
- `Content-Type`, `Content-Disposition` и политика кеша задаются явно. Поддержка Range не обещается автоматически; её необходимость и HTTP-поведение определяются отдельно.

## Публикация и кеш

Динамическая выдача из авторитетной БД — первый корректный вариант. При добавлении кеша разделяются публичные представления и защищённые ответы. Публикационная версия/поколение, если оно используется, изменяется в той же БД-транзакции, что и состояние документа; ключи и инвалидация опираются на этот результат.

Нельзя считать worker-local fallback общей инвалидацией. После commit сбой cache backend должен приводить к определённому безопасному пути: чтению актуальных данных или отказу соответствующего кешируемого пути, а не возврату закрытого содержимого. Если для этого потребуется durable invalidation/outbox, его вводят отдельной задачей вместе с тестом сбоя; для первого некешируемого каталога он не нужен.

Для HTTP-кеша задаются freshness, validators и варианты представления по [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html). Снятие с публикации прекращает новую выдачу приложением согласно выбранной политике. Уже скачанные копии и ранее разрешённый срок хранения у клиента нельзя объявить мгновенно отзывными. Поэтому политика долгого кеширования файла согласуется до её включения.

## Доступность и содержание

Технический ориентир примера — [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/). В приёмку входят последовательная структура страницы, понятные ссылки скачивания со сведениями о файле, клавиатура и видимый фокус, подписи полей, связанные ошибки и сообщения о результате. Проверяется полный процесс, включая вход и отказ отправки формы.

Доступность самого PDF и достоверность содержания принадлежат процессу подготовки документов приложения. Доступная HTML-карточка не делает автоматически доступным вложенный файл. Результат проверки примера не является заявлением о соответствии требованиям конкретного муниципального или государственного сайта.

| Публичное чтение | Разработчик собирает ограниченный список, карточку и download без installer и неиспользуемых интеграций. Путь работает с БД без JavaScript/сессии; черновик/withdrawn не раскрываются, HTML-вывод безопасен, HEAD/ошибки согласованы. После реализации сохранены SQL/latency/memory замеры на заявленных runtime и ручная проверка интерфейса |
| Редактирование черновика | Разрешённый пользователь проходит вход → создание/редактирование → upload → сохранение. Отсутствующие права/сессия/CSRF и недопустимый файл не меняют данные; redirect предотвращает обычный повтор формы; конфликты выявляются. Проверены migration failure/retry/recovery, сбои БД/audit/файлов и безопасная уборка orphan |
| Публикация | Опубликовать и снять документ можно только разрешённым действием; состояние и audit фиксируются согласованно. При уже включённом cache проверяются два независимых процесса, отказ backend и условные запросы/304. Для завершения итерации необязательный cache не требуется |
| Эксплуатация и целевое улучшение | Архив запускается на выбранной платформе, миграции отделены от ядра, backup/restore восстанавливает БД и файлы согласованно, в логах нет секретов. Улучшения дорогих путей подтверждены сопоставимыми замерами при сохранённой корректности; влияние на простоту использования и полезную функциональность объяснено |

Интеграционные тесты используют изолированную тестовую БД, а файловые проверки — отдельный временный storage. Для каждой итерации описываются простота запуска/изменения, завершённый пользовательский путь и его измеренная стоимость по [принципам](./principles.md). Конкретные latency/memory budgets выбираются по baseline, а не заимствуются из старых k6 thresholds. Завершённость одного этапа не объявляет автоматически готовыми последующие.

## Отложенные расширения

- Поиск по PDF, OCR, rich text, управление страницами, сложное согласование и расписание публикаций — после подтверждённого сценария, без превращения примера в CMS.
- Государственные реестры, юридически значимая подпись, публичные обращения и персональные данные — отдельные прикладные задачи и модели эксплуатации.
- Статический export, CDN, очередь, распределённый cache/outbox — после измеренной потребности и проверки отказов; динамический каталог работает самостоятельно.
- SPA и отдельная frontend-сборка не являются обязательными шагами. Новые возможности добавляются небольшими композициями, а не расширением `Platform` по умолчанию.
