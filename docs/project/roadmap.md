# Направления развития ядра

Тип: `roadmap`. Статус: `accepted-plan`. Сверено с кодом: 2026-10-20.

Продукт — конкретная [HTTP/PDO-основа](vision.md). [Простота, полезная функциональность и эффективность](principles.md) обязательны вместе. Сохранение наследства API-шаблона и накопление optional-подсистем не являются направлением развития.

## Проверенная база

- Автономные runtime, SQL codegen и quality tools; проверки и runtime archive без package installation/download.
- Общие App/RequestHandler, SAPI/FPM/RoadRunner, явные маршруты, 404/405/Allow/HEAD, выбор ErrorResponse.
- AttachmentResponse, прозрачная metadata-диагностика и завершение streams; [проверки/замер](../history/2026-10-18-file-responses.md) выбранного файлового пути.
- PostgreSQL PDO/параметры/транзакции/миграции, typed queries и явный LIMIT; [границы SQL](../design/sql-gen-product.md) проверяются через настоящий PostgreSQL.
- Каталог как потребитель: ограниченный список, карточка, private PDF attachment. Это приложение, а не направление CMS.
- [Очистка состава](../history/2026-10-20-core-scope.md): удалены старый API, sessions/GeoIP/fingerprints/statistics/cache, protobuf generation, hydration/mapping и outgoing HTTP. Общие точки входа согласованы.

Начальные [JSON/SELECT](../history/2026-10-17-core-http-baseline.md) и [catalog](../history/2026-10-17-public-catalog.md) отчёты описывают прежние состояния кода. Они не выбирают основной runtime и не гарантируют production readiness.

## Следующие ограниченные задачи

| Задача | Конкретный потребитель/проблема | Проверяемый результат |
| --- | --- | --- |
| Контракт чтения одной строки | SqlExecutor.fetchOne сейчас сначала получает fetchAll; lookup каталога существует | Явно определены кардинальность, объём чтения и стоимость; SQL не получает скрытые переписывания |
| Восстановление после ошибок БД | Storage.transaction и последовательные migration DDL уже используются | Реальный PostgreSQL подтверждает состояние транзакции/версий после ошибки и возможность следующей операции |
| Границы входящего HTTP | SapiRequestFactory уже переносит raw body/parsed forms/uploads | Конкретный сценарий фиксирует допустимые размеры/ошибки до расширения API; проверки через реальные transports |

Это отдельные задачи, не заказ на новую подсистему. Для каждой сначала показать текущего потребителя, минимальный API, шаги разработчика и сравнимые затраты, затем реализовывать. Сессии, редактор, auth framework, общий cache или повторное введение protobuf не следуют автоматически из таблицы.

Основной runtime и бюджеты выбираются по сравнимым данным, включая CPU/RSS всех нужных процессов. Для долгоживущего worker нужны длительные проверки памяти/состояния; короткие локальные серии недостаточны. Лицензия, версия/срок поддержки и политика обновлений собственного кода пока открыты.
